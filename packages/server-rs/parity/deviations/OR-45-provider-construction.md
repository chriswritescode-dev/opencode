# OR-45: provider configuration failures differ in timing and error class

TypeScript: OpenAI-compatible `configure` only copies `baseURL` into the route endpoint and never validates it (`packages/ai/src/providers/openai-compatible.ts:37-59`, `packages/ai/src/providers/openai-compatible-responses.ts:28-42`), so `configure({})` does not throw. Selecting a language model then throws `ProviderConfigurationError` from the shared guard in `packages/ai/src/route/client.ts:122-138` (`:128-133`); the entrypoints at `openai-compatible.ts:89-90` and `openai-compatible-responses.ts:49-52` run that path. Embedding, image and decision models from the same facade (`openai-compatible.ts:48-79`) have no guard and fail only when the request URL is rendered, where `new URL(...)` at `packages/ai/src/route/endpoint.ts:58` throws a `TypeError` inside `Endpoint.render` (`:54-62`). Alibaba throws `ProviderConfigurationError` synchronously in `configure` for `Alibaba requires region or baseURL` and `Alibaba region ${region} requires workspaceID or baseURL` (`packages/ai/src/providers/alibaba.ts:89-105`). Azure builds the endpoint with `new URL(input.baseURL)` (`packages/ai/src/providers/azure.ts:122-129`, parse at `:127`), so responses, chat, image and embedding throw a `TypeError` during configuration, while messages (`:146-159`) builds no URL and fails later (pinned `e54fbacb3d3aebc85f0e5ada0a5c490cc9333a91`).

Rust: every OpenAI-compatible entrypoint rejects an absent `baseURL` before building a route, returning `InvalidRequest` with `OpenAI-compatible providers require a baseURL` (`crates/ai/src/providers/openai_compatible.rs:24-114`, error at `:120-131`; `crates/ai/src/providers/openai_compatible_responses.rs:14-44`, error at `:42-53`). Alibaba's `base_url` returns the same two messages as `invalid_request` (`crates/ai/src/providers/alibaba.rs:140-154`). Azure accepts any `baseURL`: `openai_target` (`crates/ai/src/providers/azure.rs:162-188`) keeps the string, and `is_azure_host` (`:203-208`) returns false when `Url::parse` fails, so the malformed value takes the custom-host branch at `:180-181`, dropping the `/v1` suffix and `api-version` query (deployment URLs still append `/deployments/{model}` at `:179`). Construction succeeds and only request-time `Endpoint::render` (`crates/ai/src/route/endpoint.rs:73-95`, parse at `:82-88`) reports `Invalid endpoint URL: ...` as `invalid_request`. Rust also registers settings-based speech and transcription entry points (`ProviderPackages` `speech()` and `transcription()` tables at `crates/ai/src/providers/mod.rs:292-305`, looked up by `speech()` at `:342-351` and `transcription()` at `:364-373`) that the pinned package does not have: TypeScript exposes those modalities only on `configure(input)` as `.speech` and `.transcription` (for example `packages/ai/src/providers/cartesia.ts:18-25`). In Rust every settings key a provider does not declare becomes a provider option (`crates/ai/src/providers/mod.rs:74-82`, `crates/ai/src/providers/settings.rs:56-75`), so an undeclared speech or transcription setting is forwarded as a provider option.

Reason: the port surfaces every local provider failure as one typed `AiError` reason and builds routes eagerly through `Result`, while TypeScript reserves `ProviderConfigurationError` for facade configuration and lets URL parsing fail as a JavaScript `TypeError`; `ProviderConfigurationError` is explicitly not an `AIError` reason (`packages/ai/src/schema/errors.ts:56-68`). The provider-entry corpus (`crates/ai/tests/corpus/provider-entries.json`, replayed by `crates/ai/tests/all/provider_entries.rs`) records only a message, never a class or the construction-versus-request stage: `alibaba:missing-region` and `azure:missing-resource` cover those two message texts. No provider-entry case omits `baseURL` for `openai-compatible` or `openai-compatible-responses`, Alibaba's unknown-region message has no case, and no cassette uses a malformed Azure URL — `azure:custom` uses a valid fixture URL.
