# OR-45: Google ADC supports only authorized users, service accounts and the metadata server

TypeScript: `packages/ai/src/providers/google-vertex-shared.ts:11-34` subclasses `GoogleAuth` so the well-known ADC file lookup honours `CLOUDSDK_CONFIG`, expands `~` with `os.homedir()`, and returns `new CloudSDKAuth({ projectId: project, scopes: [SCOPE] }).getClient()`. `:87-104` caches that client per route, reads `getAccessToken()`, and maps any failure, including an empty token, to `MissingCredentialError("Google Application Default Credentials")`. `:106-115` selects ADC only when neither `accessToken` nor `auth` is configured. The cached client is google-auth-library's ADC chain (`GoogleAuth.getApplicationDefaultAsync`, `_tryGetApplicationCredentialsFromEnvironmentVariable`, `_tryGetApplicationCredentialsFromWellKnownFile`, `_checkIsGCE`) backed by `JWT`, `UserRefreshClient`, `Compute`, workload identity federation, service-account impersonation, `external_account_authorized_user` and gcloud or metadata project discovery (`e54fbacb3d3aebc85f0e5ada0a5c490cc9333a91`).

Rust: `crates/ai/src/providers/google_adc.rs:97-129` implements `CredentialSource` for `GoogleAdc`, whose `prepare` resolves once and caches a session; `:142-160` checks `GOOGLE_APPLICATION_CREDENTIALS` then `google_application_credentials` and fails instead of falling back, and `:163-179` reads the well-known file from `CLOUDSDK_CONFIG` or the platform home. `:186-207` accepts only `authorized_user` and `service_account`; every failure (unreadable file, invalid JSON, unsupported type, HTTP problem, malformed response, signing failure, empty token, unavailable metadata) becomes the single `Authentication` error built at `:395-403`. Tokens come from `:279-287` (authorized-user refresh form), `:289-305` with `:307-321` PEM decoding (RS256 service-account assertion), or `:323-331` (metadata token endpoint), with `:350-375` parsing the response and `:388-393` applying the five-minute eager refresh. The detection probe (`:237-248`) and the metadata token request (`:254-277`) abort after the 3000 ms `METADATA_TIMEOUT` (`:27`), so an unreachable metadata server fails fast instead of waiting for the OS connect timeout. `crates/ai/src/providers/google_vertex_shared.rs:80-82` returns this source from `adc`, so an otherwise unconfigured Vertex route authorizes through ADC.

Reason: the port uses only what the pinned `getAccessToken()` path needs, and `crates/ai/tests/corpus/google-adc.json` (11 cases, 15 steps, 10 requests) covers authorized_user through `CLOUDSDK_CONFIG`, the default home path and `GOOGLE_APPLICATION_CREDENTIALS`, exact service-account JWT bytes, caching and eager refresh, the three missing-credential paths, and metadata detection plus the token flow. Seven differences remain. (a) Only `authorized_user`, `service_account` and the metadata server are supported; workload identity federation, service-account impersonation and `external_account_authorized_user` report the ADC authentication error instead of running their STS or impersonation flows. (b) Metadata detection probes one deterministic base URL (`GCE_METADATA_IP`, else `GCE_METADATA_HOST`, else `169.254.169.254`) instead of racing the primary host with `metadata.google.internal`, and `bios-only` behaves like a probe instead of reading BIOS residency. (c) `HOME`, `USERPROFILE` and `APPDATA` replace `os.homedir()`. (d) No `gcloud config` or metadata project-id probe runs and no `x-goog-user-project` header is sent, because `getAccessToken()` does not add one. (e) ADC token requests carry only the protocol headers (`content-type` or `metadata-flavor`), not google-auth-library's `user-agent` and `x-goog-api-client` transport metadata. (f) A failed resolution is not cached, so a later call on the same route resolves again, while the pinned `adc` caches the rejected client promise. (g) The metadata probe and metadata token request always fail after 3000 ms, matching gcp-metadata's `requestTimeout()` off GCP, while the pin disables that limit when `getGCPResidency()` reports GCE.
