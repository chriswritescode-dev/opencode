# OR-47: loopback OAuth callbacks reject a missing or mismatched state before anything else

TypeScript: the OpenAI and ChatGPT loopback handlers read `error`/`error_description` and the missing authorization code before comparing `state` (`packages/core/src/plugin/provider/openai.ts:77`, `:87`, `packages/core/src/plugin/provider/chatgpt.ts:129`, `:139`), so any request to the callback URL aborts the pending sign-in. DigitalOcean's `/auth/token` handler does the same for `error` and a missing access token (`packages/core/src/plugin/provider/digitalocean.ts:70`, `:72`). Poe checks `state` first but still fails the pending sign-in on a mismatch (`packages/core/src/plugin/provider/poe.ts:131`), and GitLab and Snowflake Cortex resolve a state mismatch into the same failure that ends the attempt (`packages/core/src/plugin/provider/gitlab.ts`, `snowflake-cortex.ts`).

Rust: every loopback OAuth handler in the catalog compares `state` first and, on a missing or mismatched value, answers 400 without resolving the pending attempt: `crates/catalog/src/provider_plugin/openai.rs`, `crates/catalog/src/provider_plugin/chatgpt.rs`, `crates/catalog/src/provider_plugin/digitalocean.rs`, `crates/catalog/src/provider_plugin/gitlab.rs`, `crates/catalog/src/provider_plugin/snowflake_cortex.rs` and `crates/catalog/src/provider_plugin/poe.rs`. A matching-state provider error, and a missing code or access token after a matching state, still fail the attempt with the TypeScript messages. The paste-a-redirect paths already reject a foreign state without consuming the attempt, so they keep their behavior.

Reason: a stray local request to the callback URL, such as a browser prefetch, a health check, or another local process, could otherwise cancel a sign-in that the user is still completing. A real provider error response carries the `state` it was given, so checking it first does not change the outcome of a genuine denial. A malformed DigitalOcean token body has no state, so it is now ignored instead of failing the attempt.
