# OR-46: bridge absence and construction failures report different error kinds and timing

TypeScript: an AI SDK package with no injected loader is rejected as `UnsupportedPackageError` (`packages/core/src/model-resolver.ts:236-237`; class at `:39-50`, helper at `:441-446`), and so is a model with no package specifier (`:297`). A native package that fails to load becomes `ModelInitializationError` with phase `load` (`:299-300`; `initialization` at `:448-455`, phases at `:52-53`). Construction (`:250-273`) reports a thrown `ProviderConfigurationError` as `ModelConfigurationError` (`:351-359`, class at `:56-68`) and every other cause as `ModelInitializationError` with phase `construct`; loading an AI SDK provider reports `init` (`:246`). Package settings always include `body`, even when the catalog map is empty (`:302-308`). Bedrock builds its route without touching AWS credentials: `packages/ai/src/protocols/utils/bedrock-auth.ts:140-144` returns `sigV4(defaultChain(...))`, and `defaultChain` (`:29-53`) runs the AWS provider chain before every request, so a missing AWS credential surfaces as an `Authentication` error at request time (pinned `73a0eae88de47f10068a0f9dc7a743638fa3d830`).

Rust: the `AisdkBridge` default and `NoBridge` return `Error::ModelInitialization { phase: Load, detail: "load failed for {package}" }` (`crates/catalog/src/resolver.rs:121-137`), which is what an AI SDK model reports (`:190`) and what a non-builtin package reports until OR-64 supplies a bridge (`:203-208`); `Error::UnsupportedPackage` is reserved for an empty specifier and for a package that returns the wrong model kind (`:197-200`, `:205-214`). `construction_error` (`:713-731`) classifies by `AiErrorReason::InvalidRequest` into `ModelConfiguration` (`:716-719`) and every other reason into `ModelInitialization` with `Phase::Construct` (`:720-729`); nothing in the crate produces `Phase::Init` (`:84-89`). `package_settings` inserts `body` only when the catalog map is non-empty (`:542-544`), and the resolver test asserts an empty map does not reach `options.http.body` (`crates/catalog/tests/all/resolver.rs:982`). For Bedrock, an external connection projects `auth: "sigv4"` (`:499-501`, `:536-538`), the provider resolves auth while building the model (`crates/ai/src/providers/amazon_bedrock.rs:35-40`), and `resolve_auth` fails with `Authentication` when no API key or static credentials exist (`crates/ai/src/protocols/utils/bedrock_auth.rs:88-105`); `construction_error` turns that into `ModelInitialization` during model resolution.

Reason: the bridge seam is a trait whose `NoBridge` default stands in until OR-64, and the port reports `AiError` reasons instead of the TypeScript error classes, so a missing bridge and a construction failure land in `ModelInitialization` where TypeScript distinguishes `UnsupportedPackageError` from `ModelInitializationError`; the Bedrock route validates its auth input when it is built, which moves a missing AWS credential from the first request to model resolution (`OR-44-aws-credentials.md` records the credential-source difference itself). Tests cover the no-bridge case (`rejects_aisdk_packages_without_a_bridge`, `crates/catalog/tests/all/resolver.rs:1260-1278`), the construction case (`reports_provider_configuration_errors_from_supported_packages`, `:932-983`) and Bedrock resolution with a key credential (`:1183-1194`); the eager SigV4 failure is covered at `crates/ai/tests/all/sigv4.rs:177-183`. No catalog resolver test or parity scenario resolves a Bedrock model with an external connection: the parity sandbox defines only `@ai-sdk/openai-compatible` and `@ai-sdk/anthropic` providers (`parity/lib/sandbox.ts:69-70`), and `catalog-fixture` adds only an `openai-compatible` model, so neither `catalog-fixture` nor `catalog-routes` constructs Bedrock at all.
