# server-rs

The Rust replacement for the TypeScript OpenCode server process, the `opencode-server` binary. The root
`AGENTS.md` applies too.

## Build

- Run cargo through the package script, for example `bun run --cwd packages/server-rs cargo check -p opencode-server`.
- `rust-toolchain.toml` pins the toolchain and must equal `packages/cli-rs/rust-toolchain.toml`.
- This is its own Cargo workspace and never joins cli-rs's, and no root `Cargo.toml` is added.
- `opencode-local` and `opencode-util`, and `opencode-service` and `opencode-api` as test clients, come from
  `packages/cli-rs` by path and are never edited from here.
- `opencode-api-types` also comes from `packages/cli-rs` by path, but is used at runtime only for its `js` helpers
  (`number_to_string`, `parse_number`, `encode_component`, `decode_component`); the server never uses its generated
  wire types.
- This workspace has its own `Cargo.lock`, so the cli-rs crates build here against dependency versions that can
  differ from `packages/cli-rs/Cargo.lock`; update it on its own schedule with `bun run cargo update`.

## Layout

- Crate directories are `crates/<name>` with package name `opencode-<name>`.
- Declare every crate and third-party dependency once in `[workspace.dependencies]`.
- Each task adds the crate it needs, following the indicative split in project.md `Modules.md`: contract, storage,
  bus, config, location, ai, catalog, tool, fs, shell, vcs, session, mcp, sidecar, plugin, http and server, plus
  `host/` for the sidecar's TypeScript and `parity/`.
- The wire contract is the generated `opencode-contract` crate (`crates/contract`): the pinned OpenAPI document plus
  the generated route table, types, events, errors, request decoders and corpus. It is generated, never edited by
  hand.
- The LLM layer is the `opencode-ai` crate (`crates/ai`), the model, request, executor and protocol port of
  `packages/ai` at the pin. `script/gen/llm.ts` regenerates its corpus from those pinned TypeScript sources into
  `crates/ai/tests/corpus`, and fails unless the generated cassette set equals every `*.json` recording under
  `packages/ai/test/fixtures/recordings` (313); the corpus also holds `provider-entries.json`, `google-adc.json`,
  `realtime.json` and `multipart-fixtures.json`. The corpus is generated and never edited by hand, and
  `crates/ai/tests/all/replay.rs` replays every cassette as the parity check for the LLM layer. New protocols (OR-45)
  add scenarios to `script/llm/scenarios.ts` and regenerate rather than editing the corpus; the groups are fixed in
  `script/gen/llm.ts` and `replay.rs`, so update both with the scenarios. Providers are built only through
  `ProviderPackages`, looked up by their package specifier, so every entry point the recordings use stays reachable;
  the exception is a step marked `descriptorOnly` in `script/llm/scenarios.ts` (four cassettes: three
  `openai-responses-websocket/*` and one `bedrock-converse-thinking-binding/*`), which is built from its descriptor.
  A `ModelDescriptor` rebuilds only OR-44 base routes; OR-45 wrapper routes (for example Bedrock Mantle, Moonshot and
  MiniMax messages, or the Vertex variants) must be rebuilt from their provider package and settings, because several
  report a base protocol id (see `crates/ai/src/protocols/mod.rs` registry and `crates/ai/src/route/model.rs`
  `from_descriptor`).
- `opencode-config` (`crates/config`) ports paths, flags and configuration from the pin. `src/generated/flags.rs` is
  generated by `script/gen/flags.ts` and `tests/corpus/*.json` by `script/gen/config-corpus.ts`, so neither is edited
  by hand.
- `opencode-storage` (`crates/storage`) owns the database connection, migrations and the transaction helper. Its
  `src/generated/` and `tests/corpus/` are generated by `script/gen/storage.ts` from the pinned TypeScript, and other
  crates query their tables through its `Database` handle, which `Database::open` is the entry point for. Queries take
  a `&rusqlite::Connection`, which a `Transaction` derefs to; never call `Database::read` or `Database::transaction`
  again inside a transaction closure, because the connection mutex is not reentrant, and nest with `tx.savepoint()`.
- `opencode-bus` (`crates/bus`): publication, sequences, durable log, location routing, SSE text and the event feed.
- `opencode-location` (`crates/location`) ports the Location layer: the transform registry (`State` and external
  blocks), project identity, environments, the workspace connect seam, the Location map, lifecycle and the idle
  sweep. `crates/http/src/services.rs` is the only composer of per-Location services
  (`LocationServices`), and `opencode-storage` owns the `workspace`, `project` and `worktree` queries the crate calls. Boots and
  project changes publish `LocationEvent` on a broadcast channel that is not yet bridged to `opencode-bus` (pending
  deviation `OR-43-location-events`); session-row resolution
  waits for a `SessionLookup` from OR-49. `State` notifications are infallible (`BoxFuture<()>`), so the port omits
  three upstream cases: a failed reload notification, the observer-failure half of the batch-failure case, and the
  notification-failure premise of the group case. Calling `get()` on a `State` inside its own transform deadlocks on
  the rebuild mutex.
- `opencode-git` (`crates/git`) is the package's single owner of git execution: repository discovery and metadata
  fingerprinting, remotes and history, the shared `patch` model, clone/fetch/checkout/reset, linked worktrees, the
  snapshot store with its index and tree capture, tree diff and restore, and loose-object packing. Every git process
  spawns through its `Git` handle, so no other crate starts one. Patch fixtures in `crates/git/tests/corpus/patch.json`
  are generated by `script/gen/vcs-corpus.ts` from the pinned `VcsPatch` and never edited by hand.
- `opencode-vcs` (`crates/vcs`) ports the snapshot, VCS and worktree layer: the Location-scoped `Snapshot` service
  over `opencode-git`, the `Vcs` service with its built-in git and hg providers, the HEAD watcher that publishes
  `vcs.branch.updated`, worktree strategies and the `Worktree` service, repository parsing with the `RepositoryCache`,
  and the per-Location `Reference` sources.
- `opencode-session` (`crates/session`): projectors, the message updater, inbox, instruction and blob projection, and
  the store queries.
- `crates/session/tests/corpus/events.json` is generated by `script/gen/events.ts` from the pinned TypeScript and
  never edited by hand; a new durable event adds fixtures to `script/events/scenarios.ts` and regenerates the corpus.
- Projection settings come from `ProjectionSettings` until OR-42 wires config and flags.
- `opencode-http` (`crates/http`) is the request pipeline: authentication, CORS, cross-site protection, compression,
  dispatch, pairing and tickets.
- `opencode-server` (`crates/server`) holds the binary's own modules: CLI parsing, the foreground, stdio and service
  serve modes, registration, and the service commands.
- `opencode-sidecar` (`crates/sidecar`) is Bun discovery, the hardened start, the framed protocol and supervision;
  `host/` is the sidecar's TypeScript, bundled into `crates/sidecar/host/host.js` by `script/gen/sidecar.ts`, and its
  protocol types are generated into `host/src/protocol.gen.ts` with `OPENCODE_UPDATE_SIDECAR_PROTOCOL=1`.
- Generators read the pinned TypeScript sources through `script/upstream.ts`, which materializes
  `target/upstream/<commit>` from `git archive` at the commit in `upstream-pin`; they never read the working tree,
  which can be newer. `script/storage/typescript.ts` (the storage generator and `check:interop`) and
  `script/gen/config-corpus.ts` (the runtime corpora in `crates/config/tests/corpus`) use
  `target/upstream-core/<commit>` from `upstreamCoreTree` in `script/upstream.ts` instead, which links the upstream
  packages' `node_modules` and so needs `bun install` first.
- `bun run drift:report <commit>` from this package compares the pin with a target commit and reports changed
  operations, component schemas, events, durable members and migrations. Its `git` commands run from the
  repository top level, so it works from any directory.

## Checks

Before merging, the whole package must pass:

- `bun run cargo fmt --check`
- `bun run cargo clippy --locked --workspace --all-targets -- -D warnings`
- `bun run cargo test --locked --workspace --no-fail-fast`
- `bun run check:deny`
- `bun run check:drift`
- `bun run check:interop`
- `bun run parity:test`
- `bun run parity --candidate ts`, which also accepts `--only <parts>` (`steps,events,database,files,logs,model`) and
  `--tables <names>` to restrict what is compared without changing what a scenario runs; the parts, the table filter
  and the `events` and `logs` dependencies are documented in `parity/README.md`. The strict run of the four OR-43
  scenarios against the Rust binary needs the event feed and is due in OR-49.
- `bun run parity:snapshot`, which compares the pinned snapshot engine with the Rust one under seven git-config
  variants; it needs `bun install` because it materialises the pinned core tree.
- `bun run test:shell`, which needs `bun install` and a debug build of `opencode-server`
- `bun run test:host`

`docs/coverage.md` is regenerated with `OPENCODE_UPDATE_COVERAGE=1`.

Each crate keeps one integration test binary, `tests/all/main.rs`, with one module per area. Add tests as a module
there, not as a new `tests/*.rs`.

## Rules

- Generated files are committed and never edited by hand. Regenerate them with the generator under `script/gen/`;
  `bun run check:drift` fails when one is stale.
- Every difference from the TypeScript server needs a file in `parity/deviations/` that the owner has accepted. A
  difference without one is a failure.
- Parity is defined by `parity/` (ADR-007): a task is done when its named parity checks pass, not when its code
  is written. Each later task names the scenarios it adds.
- A new scenario passes `bun run parity --candidate ts --repeat 20` before it is committed.
- All work targets the upstream commit in `upstream-pin`. Read the TypeScript sources at that commit, for example
  `git show $(cat upstream-pin):packages/protocol/openapi.json`, whenever the checkout is newer. Only re-sync
  tasks change the pin.
- A new third-party dependency or licence needs `deny.toml` to pass and is recorded there with the crates that need
  it.
- First-attempt code is copied only by the task that `docs/salvage.md` names for it.
- The server reads its environment only through `ServerEnv`.
