# Plugins

Plugins are JavaScript modules that extend the server, and the whole server process shares one plugin layer.
`opencode-plugin` (`crates/plugin`) holds the logic: it turns the configuration into an inventory, activates and
tears plugins down, watches their files, and runs the npm and update checks. The JavaScript itself runs in the Bun
sidecar process described in `sidecar.md` on Linux and macOS; `crates/plugin` reaches it only through the
`ScriptHost` trait, which `SidecarHost` implements on top of `opencode-sidecar`. Windows has no sidecar yet, so the
host is absent there and script plugins do not load.

Built-ins are a fixed catalog. `native::builtins` is the only place that lists them, and it reads
`src/generated/builtins.rs`, generated by `script/gen/plugin.ts` from the pinned `packages/core/src/plugin/internal.ts`.
That file is generated and never edited by hand; `bun run check:drift` fails when it is stale. A later task replaces a
built-in's no-op activator with its native port without changing the list.

## How loading works

| Module        | Responsibility                                                                                                                                                                                |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `generation`  | The wire shapes shared with the sidecar: `Source` (`builtin`, `package`, `local`, `sdk`), `Features`, `Gui`, the `Activator`/`Activation` pair, one `Generation` per loaded plugin, and `Info`/`PluginState` for the inventory. |
| `native`      | `builtins()` returns the pre and post built-in generations from the generated catalog, and `guarded(id)` reports the built-ins that user configuration cannot replace.                          |
| `operations`  | Reads the `plugin` entries of the configuration and the `plugin/` and `plugins/` directories, resolves `file://` and relative targets, and turns each add into an entrypoint plus an mtime.      |
| `registry`    | Owns the activation slots, applies a new generation by diffing the previous prefix, tears activations down in reverse, records failures with their fallback, and publishes the inventory.      |
| `supervisor`  | Resolves operations into generations, applies them, listens for triggers, debounces reloads, holds readiness open while a reload runs, and closes everything on shutdown.                       |
| `update`      | The 24-hour update cycle: `check`, `resolve`, `update`, `follows` and `reject` over the npm methods, plus the change and interval broadcasts the supervisor subscribes to.                      |
| `script`      | `ScriptActivator` wires a loaded handle to the sidecar so the registry sees an ordinary `Activator`.                                                                                           |
| `sidecar`     | `SidecarHost` (Unix only), the `ScriptHost` over `opencode-sidecar`, including the restart counter the supervisor watches.                                                                     |
| `watch`       | `PluginWatcher` with a `NotifyWatcher` for real files and a `ManualWatcher` for tests.                                                                                                        |
| `router`      | Answers the sidecar's `plugin.watch` and `plugin.list` calls, keyed by Location.                                                                                                               |
| `sdk`         | `SdkPlugins` for plugins registered through the SDK, and `InstancePlugins` for those bound to a Location. The binary leaves both empty until OR-68.                                                                                      |

`operations` is where the target kinds are decided. A configuration entry that starts with `-` is a removal, a
string or object is an add, and `file://` URLs and `./` or `../` targets are resolved against the document that
declared them, or the Location directory when that is unknown. Discovered children of `plugin/` and `plugins/` are
sorted by name, so the order is stable. An absolute directory target is resolved through `ScriptHost::resolve_local`:
the server entrypoint wins over a GUI entrypoint, the resolved entrypoint must stay inside the target, and the mtime
is the newest of the entrypoints and the package's `package.json`. A directory with neither entrypoint is dropped, so
a TUI-only package never reaches the registry.

### The ScriptHost boundary

`ScriptHost` is the only seam between Rust and the plugin JavaScript. Every method is one JSON request in the sidecar
protocol; `plugin.load`, `plugin.activate`, `plugin.deactivate` and `plugin.close` carry the calling Location, and
the npm methods and `plugin.resolve` do not.

| Method          | Method name on the wire | Request                                                                | Response                                                                                     |
| --------------- | ----------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `resolve_local` | `plugin.resolve`        | `{directory}`                                                          | `{server?, tui?, rpc?, gui?}` entrypoints                                                    |
| `load`          | `plugin.load`           | `{operation, install, paths}`; the operation has no type tag           | `{pending: true}`, `{message}`, or `{handle, id, features, gui?, revision, source}`          |
| `activate`      | `plugin.activate`       | `{handle, options, location, app}`                                     | `{activation}`                                                                                |
| `deactivate`    | `plugin.deactivate`     | `{activation}`                                                         | `null`                                                                                        |
| `close_location`| `plugin.close`          | `{}`                                                                   | `null`                                                                                        |
| `npm`           | `npm.add` and friends   | `{pkg, paths}`, plus `{version}` for `npm.reject`                      | the npm service's own result                                                                 |

`load` has three outcomes. `{pending: true}` means a package target was requested with `install: false` and is not
installed yet, so the supervisor resolves a second time with installation allowed and activates what is available
now. `{message}` is a failed load: the sidecar reports `PluginModule.LoadError` with the plugin's message, and any
other transport failure becomes the generic "Plugin failed to load" message. A loaded plugin carries its handle, id,
features, optional GUI, revision and source, and the registry stores the definition under the handle.

`activate` runs the plugin's Effect in a fresh `Scope.Closeable`, one per activation. A failure is thrown as
`PluginActivationFailed` whose message is `Cause.pretty` of the Effect exit, after the scope has been closed. The
returned activation id is what `deactivate` and `close_location` use later. `deactivate` ignores an id recorded under
another Location, and `close_location` closes every scope for the Location in reverse creation order before
forgetting the Location's handles.

### The two bundles

`crates/sidecar/host/host.js` is the sidecar's entry bundle: connection, frames, the handler table and the protocol
version. `crates/sidecar/host/plugins.js` is a second bundle containing every plugin the host provides, generated by
`script/gen/sidecar.ts` from `host/src/plugin` and the pinned upstream tree. Because the plugin modules are bundled
into the sidecar, every plugin's `effect`, `@opencode/util`, `@opencode/plugin` and `@opencode/schema` import resolves
to the host's instance instead of a nested copy in the plugin's own `node_modules`; an unprovided subpath fails loudly
rather than silently loading a second copy. The generated specifier list is `host/src/plugin/runtime-modules.gen.ts`,
also written by `script/gen/sidecar.ts`. Both files are generated and never edited by hand.

### Watching and reloading

The supervisor arms a watch for each configured absolute target on every reload, through the Rust watcher rather than
the sidecar; the watcher keeps one subscription per target and re-arms it when the target changes kind. An existing
directory is watched recursively, an existing file through its parent directory filtered to that name, so an editor's
atomic replace keeps the subscription, and a missing target through its nearest existing ancestor without recursion so
a plugin created later still triggers and a mistyped target cannot become a recursive watch of `/` or `$HOME`. Only
create, modify, remove and write-close events on a watched target trigger a reload, so importing a plugin does not
retrigger it. The disable switch passed to `opencode_local::watch::disabled` turns live reload off in one place. A
change, a config update, a new SDK plugin, a new module, an interval tick, an npm change for a running package or a
sidecar restart all increment one shared trigger counter.

The supervisor's loop activates the initial generation immediately, then waits on that counter. After the first
change it keeps draining changes until 100 ms pass with none, so a burst of triggers becomes one activation. Each
activation re-resolves the configuration and the directories and applies the result; a package whose new revision
fails to load keeps its previous activation, and the generation keeps running packages that failed while the failure
appears in the inventory. A registry `Hold` keeps readiness pending for the whole reload and is released only when
the observed trigger count has settled, so a caller waiting on activation never sees the middle of a burst.

A sidecar restart is a trigger like any other. The restart counter increments once per Ready-to-Exited transition, so
a sidecar that dies before it ever reached Ready publishes nothing. On a restart the supervisor forgets the script
slots without closing them, because their sidecar state is already gone, and reloads; it retries with a growing delay
while slots stay forgotten, up to five attempts, because a restart is followed by the sidecar's own crash backoff. A
plugin that still fails after that is left to the next file, config or interval change. Local and package plugins are
activated again in the new process, while built-ins are untouched.

Shutdown closes the registry before the supervisor's tasks are aborted, so a reload in flight finishes and its
activations are closed. If an activation does not settle within five seconds, shutdown aborts the tasks and closes
again, so a plugin stuck in the sidecar cannot hold a Location open, and activations already drained by the interrupted
reload are still closed.

### Readiness

Plugins load asynchronously. Server handlers never wait for `Plugin.awaitActivation`: they answer with the inventory
as it is now, which may be empty or partial on a cold Location, and an action that needs a plugin that has not loaded
yet fails as not found. Long-lived clients refresh when they receive `plugin.updated`, which the registry publishes
only when the inventory actually changes; one-shot clients poll `GET /api/plugin` for the Location they need (the router's
`plugin.list` answers only the sidecar's own callback). Session entry points that genuinely need a built-in may wait on their side, and the
tests use the same `await_activation` so they observe a settled generation.

## What is not ported yet

- SDK plugins do not expose their own features or GUI through `SdkPlugins::register` (OR-68).
- `ctx.command` and `ctx.rpc` are unimplemented and return the OR-63 "not available" error.
- The aisdk SDK hook ordering waits for OR-64 to extend SDK plugin registration.
